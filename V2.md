# WIRING V2 — план обновления интерфейса

Дата: 12 сентября 2026. Документ для передачи агенту-исполнителю.
Статус: план реализации; приложение и публикация в рамках подготовки плана не менялись.

## 1. Задача и результат

Сделать главную WIRING компактной и понятной на телефоне: сразу показать назначение сервиса и переход к знакомствам, убрать постоянно раскрытое облако диагнозов, привести навигацию к устойчивой структуре. Сохранить характер бренда: WIRING, спокойный лавандовый фон, выразительный заголовок с засечками, простые элементы управления.

Текущая проблема на пользовательском мобильном скриншоте: шапка переносится на несколько строк, большой заголовок и облако ярлыков вытесняют основной CTA за видимую область браузера. Простое уменьшение всей страницы не решает проблему: требуется изменить порядок и плотность блоков.

Пользователь попросил именно план для другого агента. Реализация по этому документу — отдельная работа. Деплой не входит в результат плана и не должен выполняться автоматически при его чтении.

## 2. Референсы и принятые решения

Оба присланных изображения показывают **главную**, а не два разных функциональных экрана. Не трактовать второй как ленту или профиль.

- [Основной референс: главная с людьми](docs/design-v2/home-with-people.jpg).
- [Дополнительный референс: минимальная главная](docs/design-v2/home-minimal.png).

Рекомендуемая композиция: первый референс с тремя портретами; компактная шапка со вторым референсом как ориентиром. Это проектное решение плана, а не отдельное подтверждение пользователем каждого элемента.

Из первого берём короткий заголовок «Свои люди рядом.», ряд фотографий, заметный CTA, свёрнутые особенности и нижнюю навигацию. Из второго — единичную кнопку темы вместо трёх постоянно видимых свотчей и спокойную визуальную плотность. Не переносить огромные отступы и размеры текста из растровых изображений буквально. Большую декоративную линию второго референса не добавлять.

Ранние концепты со свайп-карточкой и большой иллюстрацией кафе не являются целевыми референсами V2.

## 3. Реальный код проекта

Проект использует Flask и обычный JavaScript, без React и сборщика фронтенда. Не мигрировать стек ради редизайна.

| Файл / участок | Назначение и план изменений |
| --- | --- |
| `public/app.js`: `homeView()` | Новая композиция главной; раздельные сценарии посетителя, гостя и пользователя |
| `public/app.js`: `nav()`, `hrefFor()`, `parseRoute()`, `render()` | Общая шапка и мобильная навигация с сохранением маршрутизации и обработчиков |
| `public/app.js`: `themeSwatches()`, `applyTheme()`, `THEMES` | Компактный выбор существующих трёх тем |
| `public/app.js`: `deckView()`, `personView()`, `likesView()`, `matchesView()`, `chatView()`, `profileView()` | Проверка совместимости общего оформления, отступов и навигации |
| `public/styles.css` | Размеры, сетка, состояния, темы, адаптивность, безопасные отступы |
| `templates/index.html` | Оболочка, подключение стилей и скрипта, раннее восстановление темы; обновить версии ресурсов после реализации |
| `public/people/`, `public/portraits/` | Возможные источники декоративных портретов; предварительно проверить происхождение и пригодность |
| `tests/test_app.py`, `tests/test_logic.py` | Существующие функциональные проверки |
| `app.py` | Backend; менять только при выявленной необходимости, не ради вёрстки |

В рабочем дереве уже много изменённых и новых файлов. Перед реализацией сохранить понимание текущего diff. Не сбрасывать, не перезаписывать и не присваивать себе чужие изменения. Номера строк не фиксируются: искать указанные функции по именам.

## 4. Главная: порядок элементов

1. Однострочная шапка: логотип слева; кнопка оформления и профиль справа. Для посетителя вместо чужого аватара — понятный вход. Логотип ведёт на главную.
2. Заголовок: «Свои люди рядом.» На узком экране допустим естественный перенос в две строки.
3. Подзаголовок: «Знакомства для нейроотличных. В своём ритме.»
4. Три небольших портрета в один ряд, одинакового размера, с аккуратным кадрированием.
5. Основная кнопка: «Перейти в ленту» для пользователя и гостя. Сценарий посетителя описан ниже.
6. Закрытый по умолчанию блок «Мои особенности», подпись «Ярлыки — по желанию».
7. Ссылка «Как устроен WIRING»: раскрывает короткую справку на странице. В справке объяснить профиль, ленту и взаимные симпатии; дать рабочую ссылку на `/glossary`.
8. Тихая подпись «Можно быть собой.» и ссылки «18+», «Правила», «Конфиденциальность».
9. Нижняя навигация на мобильном: «Главная», «Лента», «Лайки», «Чаты».

На первом экране обязательно виден основной CTA. Не требовать, чтобы весь подвал помещался без прокрутки на любом телефоне. При крупном шрифте доступность важнее размещения всего контента на одном экране.

### Портреты

Использовать локальные декоративные изображения взрослых людей с проверенным происхождением; при необходимости подготовить отдельные оптимизированные ассеты. Не вырезать UI целиком из референса и не подменять работающую страницу картинкой. Не выдавать декоративные лица за реальных пользователей рядом, не приписывать им диагнозы, онлайн-статус, расстояние или количество лайков. Не брать частные фото из базы приложения для публичной главной.

Задать `width`/`height` или `aspect-ratio`, чтобы исключить скачок страницы. Для декоративного ряда использовать пустой `alt`; не делать изображения ложными кликабельными карточками. При отсутствии изображения — спокойный фон без сломанной иконки. Компактный вариант без портретов допустим как резерв при недоступных ассетах, а не как дополнительный обязательный экран.

## 5. Поведение и состояния пользователя

| Состояние | Главная кнопка и дополнительные действия |
| --- | --- |
| Авторизованный пользователь | «Перейти в ленту» через существующую навигацию; при незавершённом onboarding сохранить текущую проверку и переход |
| Уже созданная гостевая сессия | «Перейти в ленту»; сохранить ограничения гостя и предложение регистрации |
| Посетитель без сессии | «Смотреть знакомства» запускает существующий сценарий `#demo` → `POST /api/demo` → загрузка ленты; ниже компактные ссылки «Создать профиль» и «Войти» |

Не превращать демо-вход в незаметную регистрацию. При запросе показывать занятость кнопки, защищаться от повторного нажатия; при ошибке объяснять сбой и разрешать повтор. Не менять правила доступа к лайкам, сообщениям, фотографиям или платным возможностям.

### Особенности: важное различие

Сейчас облако в `homeView()` для авторизованного человека **фильтрует ленту**, а для посетителя переносит выбранный ярлык в регистрацию. Оно не является редактором собственной анкеты. Нельзя просто переименовать его в «Мои особенности» и оставить старое поведение.

Для V2 закрытый блок раскрывает краткое объяснение и ссылку «Изменить в профиле» для зарегистрированного пользователя. Можно вывести уже сохранённые собственные ярлыки, используя каталог для подписей. Редактирование остаётся в существующем профиле, без нового механизма сохранения на главной. Для посетителя и гостя — «Добавить при создании профиля», ведущая к регистрации, без обязательного выбора. Фильтрация людей остаётся в фильтрах ленты. Пустые особенности — нормальное состояние.

Кнопка раскрытия имеет `aria-expanded`, `aria-controls`, работает с клавиатуры. Открытие не должно запускать переход или отправку данных. Ссылку на внешний тест убрать из ряда основных действий главной; не добавлять новые диагностические обещания.

### Темы

Постоянные три цветных квадрата заменить одной кнопкой «Оформление», раскрывающей небольшой выбор тем. Сохранить `pastel`, `mist`, `night`, существующий ключ `wiring-theme` и восстановление темы до отрисовки. Для нового посетителя рекомендуемый вид V2 — `mist`; это решение применить согласованно в JS, CSS fallback и раннем скрипте шаблона. Уже сохранённый выбор не менять. Все темы остаются доступны, в том числе из профиля. Размер шрифта не делать новой настройкой в рамках этой работы; обязательно поддержать системное увеличение и браузерный масштаб.

## 6. Общая навигация и остальные экраны

Сохранить существующие пути:

| Пункт | URL | Активное состояние |
| --- | --- | --- |
| Главная | `/` | `home` |
| Лента | `/feed` | `deck`, а также открытая из ленты анкета |
| Лайки | `/likes` | `likes` |
| Чаты | `/chats` | `matches`, `chat` |
| Аватар / профиль | `/me` | `profile` |

Использовать `hrefFor()` и `data-nav`, сохранить `BASE`, прямое открытие URL, обновление страницы и кнопки назад/вперёд. Для вложенной анкеты по возможности учитывать `personFrom`, не сбрасывая контекст возврата. Счётчики лайков и непрочитанного брать из существующего состояния, не рисовать фиктивные точки. В навигации использовать `aria-current` и подписи к иконкам.

На мобильном общая навигация закреплена снизу на главной, ленте, лайках и списке чатов. В открытом диалоге приоритет у поля сообщения: разместить его над безопасной нижней зоной, а общий таббар скрыть, оставив понятный возврат к чатам. Проверить клавиатуру. На входе, регистрации и onboarding не добавлять отвлекающую закреплённую навигацию. Для защищённых пунктов посетителя сохранять текущий вход с возвратом в запрошенный раздел; не создавать гостя от любого клика по навигации.

Изменения остальных экранов ограничить общим оформлением, отступами и корректной навигацией. Два референса не задают новый дизайн свайп-карточки, чата или редактора профиля. Не придумывать полный редизайн этих экранов и новые возможности в рамках V2.

## 7. Размеры и адаптивность

Все размеры ниже — стартовые CSS-ориентиры, уточняемые в браузере, не пиксели изображения.

- Телефон: боковые поля 16–20 px, шапка около 56–64 px, логотип 24–28 px, заголовок 30–36 px с межстрочным 1.08–1.15, основной текст 16 px.
- Кнопка CTA: минимум 48–52 px по высоте, ширина контейнера. Интерактивные области не меньше 44 × 44 px.
- Портреты: три равных столбца, зазор 8–12 px, высота примерно 100–125 px на ширине 390 px. Не увеличивать их до размера свайп-карт.
- Отступы между смысловыми блоками 16–24 px; внутри связанных элементов 8–12 px. Скругления 14–20 px, тонкая граница, минимум теней.
- Мобильный таббар: около 60–64 px плюс `env(safe-area-inset-bottom)`; контент получает соответствующий нижний padding. Не закрывать футер, кнопки, модальные окна и поля.
- Использовать гибкий размер по содержимому и `min-height`, избегать фиксированной высоты всей страницы и обрезания `overflow: hidden`. При необходимости использовать `dvh` с безопасным fallback.
- Планшет и desktop от ориентировочных 768 px: навигация в верхней строке вместо нижнего таббара. Компактный центрированный блок главной, максимум около 720–840 px; не растягивать текст и фото на весь монитор. На промежуточных ширинах выбирать раскладку по фактическому помещению элементов.
- Существующие Fraunces и IBM Plex Sans оставить при условии корректного рендеринга кириллицы; проверить реальный fallback. Не подключать новые шрифты без необходимости.
- Сохранить клавиатурный фокус, читаемый контраст во всех темах, увеличение текста до 200% и отсутствие зависимости от hover. Не добавлять автоматическую карусель или обязательную анимацию.

## 8. Порядок реализации

1. **Зафиксировать исходное состояние.** Прочитать инструкции, изучить текущий diff, запустить локально и снять главную для посетителя, гостя и пользователя на мобильной и большой ширине. Проверить существующие тесты до правок, записать исходные сбои.
2. **Подготовить основу оформления.** Добавить scoped-классы новой главной и общей оболочки. Не править глобальные `h1`, `.panel`, `.actions` так, чтобы незаметно сломать формы или ленту. Расширить существующий набор SVG-иконок.
3. **Собрать главную.** Реализовать порядок блоков, портреты, тексты, CTA по состояниям пользователя, раскрытие особенностей и справки. Переиспользовать существующие навигацию, каталог и профиль.
4. **Переделать общую навигацию и оформление.** Компактная шапка, выбор темы, таббар на телефонах, верхние ссылки на больших экранах, активность и реальные счётчики.
5. **Проверить остальные экраны.** Лента, просмотр анкеты, лайки, чаты, диалог с клавиатурой, профиль, вход и onboarding; устранить регрессии от общей оболочки.
6. **Проверить адаптивность и доступность.** Скорректировать размеры по фактическому viewport браузера, а не по высоте скриншота без браузерных панелей.
7. **Подготовить результат для ревью.** Обновить версии CSS/JS в шаблоне, приложить скриншоты и отчёт о проверках. Публикацию выполнять только в рамках отдельного поручения.

## 9. Проверки и критерии готовности

### Визуальная матрица

Проверить viewport 320×568, 390×664, 390×844, 430×932, 768×1024 и 1440×900. Размер 390×664 специально моделирует уменьшенную доступную высоту из-за панелей браузера. Дополнительно проверить мобильный Safari и Chrome с панелями браузера; если реального устройства нет, прямо указать ограничение проверки.

- Основная кнопка полностью видна без прокрутки при стандартном размере текста на 390×664; на самом маленьком viewport сократить отступы и портреты прежде, чем уменьшать читаемый шрифт.
- Шапка не распадается на строки, горизонтального скролла нет на всех ширинах.
- Ярлыки закрыты при входе; раскрытие не перекрывает CTA или навигацию и не меняет анкету автоматически.
- Нижний таббар не перекрывает контент и учитывает safe area.
- При 200% масштабе разрешён вертикальный скролл, но все действия доступны, текст не обрезан.
- Светлые и тёмная темы читаемы; выбранная тема переживает перезагрузку.
- Все ссылки, профиль и справка работают; клавиатурный фокус виден, диалог оформления закрывается по Escape и возвращает фокус.
- Загрузка или ошибка портрета не ломает геометрию.

### Функциональная матрица

Проверить посетителя без сессии, гостя, пользователя с завершённым и незавершённым onboarding. Проверить пустые ярлыки, отсутствие аватара, пустые лайки и чаты, ненулевые счётчики, ошибку демо-входа. После навигации и обновления URL пользователь остаётся в ожидаемом разделе. Проверить фильтры, свайп, открытие анкеты и возврат, получение списка чатов, отправку тестового сообщения только в локальной тестовой среде.

Для входа в **локальный** сайт при браузерных проверках использовать тестовых пользователей из README: основной вход `dev@wiring.test` / `wiring-dev` (Дев); для чатов есть собеседник `peer@wiring.test` (Пир). http://127.0.0.1:5070/

Запуск существующих проверок из README:

```sh
python3 -m unittest discover -s tests -q
```

Использовать окружение проекта с установленными зависимостями. Не считать успешные Python-тесты проверкой внешнего вида. Дополнительно выполнить браузерную проверку сценариев и отсутствие JS-ошибок. Новые автоматические тесты добавлять для изменившегося поведения навигации/состояний, если есть подходящая инфраструктура; не заводить большой новый тестовый стек ради статических отступов. Сетевые действия проверять на локальных данных, без сообщений реальным людям.

## 10. Что передать после реализации

- Краткое описание изменений и перечень затронутых файлов.
- Скриншоты новой главной на телефоне с небольшой доступной высотой и на desktop; отдельно открытые особенности и выбор темы.
- Результат функциональных проверок и список ограничений или оставшихся проблем.
- Подтверждение сохранения гостевого режима, регистрации, профиля, фильтров, чатов и сохранённой темы.

Готовность V2 определяется работающей компактной главной и отсутствием регрессий, а не буквальным совпадением с растровым изображением. Не добавлять новые продуктовые обещания, статистику, платные возможности или полный редизайн остальных экранов без отдельной задачи.
