# WIRING Mobile — план разработки приложения для iOS и Android

Дата: 30 сентября 2026. Основа: разбор репозитория https://github.com/volodymyrk8/wiring (Flask + PostgreSQL 16 + Preact/TS SPA, ~60 JSON-эндпоинтов `/api/*`, Web Push, PWA-манифест).

## 1. Контекст

WIRING — знакомства для нейроотличных: анкета (фото, альбомы, теги neuro/vibe, намерения, город), лента со свайпом, лайки, мэтчи, чаты (текст, фото, голос с расшифровкой), блок и жалобы, WIRING+ (подписка), Jev-ранжирование (эксперимент), гостевой режим.

Что важно для мобильного клиента:

| Факт о бэкенде | Следствие |
|---|---|
| Авторизация — cookie-сессия Flask (`session["uid"]`) | В нативном клиенте cookie хранит системный сетевой стек (NSURLSession / OkHttp), поэтому MVP работает без изменений сервера. Для продакшена нужны токены (фаза 1). |
| Чат опрашивает `/api/messages/<id>` целиком каждые 8 с | Пагинация и push нужны до публичного релиза. |
| Push только Web Push (VAPID) | Нужны токены устройств и APNs/FCM. |
| Фото отдаются относительными путями (`/public/...`, `/media/...`) | Клиент дописывает базовый URL. |
| Удаление аккаунта, блок, жалобы, согласия уже есть | Закрывает ключевые требования сторов к UGC-приложениям. |
| Нет OpenAPI | Типы ответов фиксируем в `mobile/src/api/types.ts`. |

## 2. Решение: Expo (React Native + TypeScript)

| Вариант | Оценка |
|---|---|
| **Expo / React Native (выбран)** | Одна кодовая база для iOS и Android, тот же язык, что во фронтенде. Нативные жесты, камера, push, Keychain. Низкий риск отказа сторов. |
| Capacitor (обёртка SPA) | Быстро, но риск отказа Apple по 4.2, слабее свайпы и клавиатура. Не выбран. |
| Swift + Kotlin | Вдвое дороже. Не оправдано. |

Стек: Expo SDK, Expo Router, TypeScript, TanStack Query, expo-secure-store, expo-image-picker, expo-notifications, expo-av, Sentry, EAS Build/Submit.

## 3. Фазы

### Фаза 0. Подготовка (1–1,5 недели)
- ADR по выбору Expo; структура `mobile/` рядом с бэкендом.
- Аккаунты Apple Developer и Google Play, bundle id, EAS.
- UI-кит из V2 (три темы, компактная шапка, нижняя навигация).
- Юридика: 18+, данные о здоровье (нейротип), App Privacy и Data Safety.

### Фаза 1. Бэкенд для мобильных клиентов (2 недели) — критический путь
1. Токен-авторизация: `POST /api/auth/token` (access + refresh), `Authorization: Bearer`, ротация и отзыв refresh. Cookie для веба остаётся.
2. Версионирование: `X-App-Version`, минимальная поддерживаемая версия, экран «обновите приложение».
3. Нативный push: таблица `device_tokens`, отправка через FCM/APNs, переиспользовать логику `notify.py` и `push.py`.
4. Чат: `GET /api/messages/<id>?after=&limit=`, ключ идемпотентности при отправке, затем SSE/WebSocket.
5. Медиа: HEIC/HEVC, лимиты размера, сжатие (`media.py`).
6. Rate-limit для нативных клиентов.
7. Universal Links / App Links (`apple-app-site-association`, `assetlinks.json`).
Новые эндпоинты выносить в отдельный модуль, не раздувая `app.py` (правило AGENTS.md).

### Фаза 2. MVP приложения (5–6 недель)
1. Каркас: навигация, темы, API-клиент, ошибки и офлайн, Sentry.
2. Авторизация: вход, регистрация (18+, согласие), забыл пароль, гость.
3. Онбординг и анкета: фото, альбомы, теги, намерения, город, автосохранение с локальным черновиком.
4. Лента: карточки, свайп фото, явные «лайк» / «пропустить», откат, повтор ленты для WIRING+.
5. Профиль человека: галерея, общие теги, блок и жалоба.
6. Лайки и мэтчи: список, гейт WIRING+.
7. Чаты: список, тред, фото, голос, удаление, разматч.
8. Уведомления и настройки.
9. Аккаунт: согласия, удаление аккаунта внутри приложения, поддержка, правила, конфиденциальность.

### Фаза 3. WIRING+ (2 недели, параллельно)
Пока подписка — подарок на 90 дней, покупок нет. Если продажа появится в приложении, обязательны StoreKit / Google Play Billing (например, RevenueCat) и серверная проверка чеков, продлевающая срок в `premium.py`. Кнопок «купить» в обход сторов быть не должно.

### Фаза 4. Качество и требования сторов (2–3 недели)
- UGC: жалоба и блок доступны на каждом экране с чужим контентом, быстрая модерация (`moderation.py`, `admin.py`).
- 18+, согласия, политика по URL (`legal_pages.py`).
- Доступность: Dynamic Type, VoiceOver/TalkBack, reduced motion, контраст.
- Тесты: Jest (логика), Maestro или Detox (вход, анкета, лента, чат).
- Производительность: холодный старт, кэш изображений, FlashList.
- Приватность: не отправлять нейротип и содержимое чатов в сторонние SDK.

### Фаза 5. Бета и релиз (2–3 недели)
TestFlight и Play Internal, закрытая бета 20–50 человек, карточки сторов, демо-аккаунт для ревьюера, ревью с запасом на одну итерацию отказа, staged rollout, мониторинг ошибок и метрик (регистрация, заполнение анкеты, D1/D7).

## 4. Сроки
12–16 недель до публичного релиза для 1–2 разработчиков.

## 5. Риски
1. Ревью Apple: 4.2, 1.2 (UGC), 3.1.1 (подписки).
2. Чувствительные данные (нейротип): юридически корректные согласия, минимальная аналитика.
3. Cookie → токены: веб не ломать, тесты на оба способа.
4. Поллинг чата: батарея и трафик, пагинация и push до релиза.
5. Монолитный `app.py` (~3750 строк): мобильные эндпоинты в отдельный модуль.

## 6. Что уже сделано
- Expo-приложение (`mobile/`): вход и регистрация, лента со свайпом (жесты и кнопки), лайки, мэтчи, чат (инкрементальный опрос, история постранично), профиль человека с жалобой и блокировкой, свой профиль, редактор анкеты (фото, основное, город из списка, теги, намерения, согласия), настройки уведомлений, современный интерфейс со светлой и тёмной темами.
- Бэкенд (фаза 1, частично): токен-авторизация с ротацией refresh, версионирование клиента, push-токены устройств и отправка через Expo Push, постраничная выдача сообщений. Документация: `docs/mobile-api.md`, 18 тестов.
- Не сделано: идемпотентность отправки сообщений, SSE/WebSocket, голосовые и фото в чате, фильтры ленты, WIRING+ покупка, Sentry, тесты клиента, EAS build/submit, проверка push на реальном устройстве.
